# Webcast 当前代码审查与电视连接建议

日期：2026-10-26。基准：当前工作区 **0.1.2 (3)**，不是只看 Git HEAD。技术栈为 SwiftUI / WKWebView / Google Cast iOS SDK 4.8.6；没有项目运营的后端或视频代理。本轮只增加审查文档、隔离探针和验证证据，没有修改业务源码、测试套件、项目配置或依赖，没有安装 App、连接或控制电视。

## 结论

**继续完善现有 Chromecast 方案最合适。现有自动化回归通过，但长期稳定性的主要证据缺口仍在真实接收端、异常网络和持续播放。** 不建议先做 Wi-Fi Direct、自建电视 App 或手机视频代理。

已确认网页可伪造视频候选及“当前视频”状态，候选模型还接纳无长度上限的部分元数据。尚未确认远程代码执行、跨站 Cookie 窃取或网页绕过用户操作直接投屏的漏洞。输入资源约束与可信度标记应先于功能扩张；不能把“没有发现高危利用链”写成“系统安全”。

## 安全发现

优先级含义：P1 为下一轮稳定化应完成，P2 为后续加固；不是 CVSS 评级。

### S1 / P1：桥接输入的字节与频率预算不完整

- 位置：`Webcast/Models/VideoCandidate.swift:148`、`Webcast/Sniffer/VideoSniffer.swift:54`。
- 已有防护：URL 最多 16384 字符、标题截为 300 字符、frame ID 截为 100 字符、候选 100 条、已退休 frame 200 条；脚本自身的 manifest 读取有 512 KiB / 4 并发 / 5 秒预算。
- 缺口：网页可直接调用 `window.webkit.messageHandlers.videoSniffer`，绕过脚本去重和读取预算。`source`、`segmentFormat`、`pageURL`、`generation` 等没有完整的长度、枚举和结构限制；每条消息处理后还在主线程刷新排序列表，没有原生接收频率限制。
- 已复现：单个候选原样保留 1,048,576 字节 `source` 和同样大小的 `segmentFormat`。没有进行耗尽内存或让 App 崩溃的实验，洪泛导致的卡顿/退出属于需压力测试验证的风险。
- 建议：先做严格白名单解码；`source` / `segmentFormat` 变为允许的枚举；为所有字符串设 UTF-8 字节上限，限制未知键/嵌套结构。按文档和 frame 建立接收预算、去重和合并刷新，保留 route / inactive / frameGone 等生命周期消息的优先级。原生预算必须独立于可被页面改写的 JS。WebKit 消息在进入回调前已有反序列化成本，原生限流不能消除所有 IPC 成本，仍需实际压力测试及失控页面恢复入口。
- 完成标准：超长和畸形字段被丢弃；洪泛期间候选仍有界、操作可恢复、生命周期终止消息不被饿死；记录内存、CPU 和主线程响应数据。

### S2 / P2：候选和生命周期消息可被页面伪造

- 位置：`Webcast/Sniffer/VideoSniffer.swift:34`、`:58`、`:68`；`Webcast/Models/VideoCandidate.swift:159`。
- 已复现：页面先发 `type: restored`，任意新 generation 就进入接受列表；再发 `current: true`，即使页面没有 video 元素，候选也显示为当前。页面提供的 frame ID、pageURL 和 current 不是可信身份或播放证明。
- 影响：污染或替换候选、干扰 frame 生命周期和“当前视频”的优先级，诱导用户投放非预期媒体。现有 UI 展示来源 host 且需要用户点击，桥本身不调用 Cast；没有验证到静默控制电视的路径。因 fetch/src 拦截必须运行在 page world，不能把随机 generation 当秘密或把改用 isolated world 当完整解决方案。
- 建议：将网络观察明确标为网页提供/推断数据；只有受原生导航状态约束的恢复流程才能重新激活代次，不接受任意网页自报恢复；结合 `WKScriptMessage.frameInfo` 的真实来源约束 frame 操作范围。把页面观察与原生投屏授权分开，继续要求明确点击并展示真实媒体 host。投屏入口再次验证 URL/格式/上下文，不能只依赖列表按钮状态。
- 完成标准：伪造 restored、跨 frame 删除/冒充、旧页面迟到消息不会改变新页面的可信状态；网页观察再多也不能自行产生连接、加载或遥控命令。

### S3 / P2：HTTP 与私网媒体需要明确的使用边界

- 位置：`project.yml` 的 ATS 设置、`Webcast/Browser/BrowserModel.swift:267`、`Webcast/Models/VideoCandidate.swift:150`。
- 已确认：允许 WebView 加载 HTTP，模型也接受 `http://192.168.1.1/audit.mp4`。HTTP 会增加明文访问/内容被篡改的风险；若用户选择私网候选，可能让接收端访问非预期局域网资源。实际请求是否发出还受接收端网络、播放器和浏览器策略限制，本轮没有测试该请求。
- 这不是已确认的服务器 SSRF：项目没有此类服务器，当前模型接纳 URL 也不等于自动请求。局域网媒体是合理需求，不能直接封禁全部 RFC1918 地址。
- 建议：默认 HTTPS；HTTP 页面显示连接风险；公网页面引入 loopback、link-local 或私网媒体时默认拦截/明确确认，并提供用户主动启用的局域网媒体模式。若未来引入代理，应同时校验 DNS 解析、IPv4/IPv6、重定向与每一跳地址，另做 SSRF 审查。当前 `file` 导航按 demo/内部用途收窄，但没有证据支持“可任意读取沙箱文件”的结论。
- Web 内容 ATS 例外只应按用途保留，不能推论为所有原生网络请求均关闭 TLS 校验。[Apple ATS 文档](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowsarbitraryloadsinwebcontent)。

### S4 / P2：浏览隐私与调试证据

- 位置：`Webcast/Browser/BrowserModel.swift:251`、`Webcast/Cast/CastManager.swift:431`。
- 最近页面完整 URL 写入本地 UserDefaults，可能包含访问令牌或私人查询；Debug 的 SDK 日志直接输出 SDK 原始消息，分享前应按可能包含敏感 URL 处理。本轮没有确认实际令牌泄漏。
- 建议：增加“不保存上次页面/无痕”选项；无痕使用独立 `.nonPersistent()` 数据存储；保留清除网站数据的现有功能。后续诊断导出只允许白名单字段，由用户主动导出；不要把 raw NSError、Cookie 或完整媒体 URL加入日志。裁剪浏览恢复 URL可能破坏网站功能，应优先提供明确的关闭选项，而非无差别去掉所有 query。

已具备的有效防护应保留：地址和候选拒绝非 HTTP(S) 与 URL 用户名密码；DRM 候选禁用且加载入口再次检查；没有把网页字符串拼进原生执行代码；投屏确认后才按原始文档/媒体修订暂停本地；Release 关闭详细 SDK 日志和 WebView 检查；诊断仅保留 20 条内存记录且不存完整 URL；官方 Cast 归档通过固定版本 URL 与 SHA-256 锁定。`Package.resolved` 为空不代表当前二进制依赖未锁定。

建议的首次发布门槛（这是待采用的目标，不是当前测量值）：

1. 全部必需自动化通过，失败重跑保留首轮证据，不用通过的重试掩盖 flaky 测试。
2. 在家庭基准网络、受控 H.264/AAC MP4 和 HLS 上，完成每类接收端至少 20 次开始投屏循环，成功率目标 ≥95%；同时记录样本数与失败原因，小样本通过不等于生产 SLA。
3. 探索性目标：发现 p95 ≤10 秒、开始投屏至电视出声画 p95 ≤15 秒、回前台后遥控恢复 p95 ≤10 秒。发现/播放分别计时；外站受限片源不混进基准指标。
4. 每类接收端连续 2 小时受控片源播放，无 App 崩溃、无意外停止/错投；WebView/原生内存无随循环持续增长的趋势。用 Instruments 的 Allocations、Leaks、Time Profiler 与能耗工具记录基线，不臆定所有机型统一内存阈值。
5. 权限拒绝、接收端离线、403 和断网都必须给出可恢复状态；锁屏下电视是否继续播放单独记录，不能据此承诺手机锁屏遥控。

真实站点作为独立兼容矩阵：至少三集、首播/换集/签名过期重取。站点变更、CDN 鉴权与接收端固件会随时间变化，即使 App 不发版也要定期抽查。[Google 测试范围](https://developers.google.com/cast/docs/testing)。

## Chromecast 与 Wi-Fi 的关系

| 方案 | 前提 | 对当前代码的成本 | 建议 |
| --- | --- | --- | --- |
| Google Cast / Chromecast | 支持 Cast 的电视或接收器，手机与其处于可互通的本地网络，媒体源可由电视访问 | 低；已有 SDK、设备选择、默认接收器及遥控 | 首选，先验收与补强 |
| “Wi-Fi 直连”指同一家庭网络 | Wi-Fi 只是网络承载，还需要 Cast/AirPlay/DLNA 等接收协议 | 当前 Cast 已实现这一用法 | 不要作为第二套功能重复开发 |
| 真正 Wi-Fi Direct / Miracast | 两端兼容的点对点与投屏协议 | 高；当前 iOS App 没有该栈，电视支持 Wi-Fi Direct 不代表支持 Google Cast | 不作为当前 MVP 路线 |
| Wi-Fi Aware 点对点 | iOS 26+、兼容硬件、双方 Wi-Fi Aware 支持、App 服务/配对及播放协议 | 高；需双方接收能力和新传输协议，不是 Cast 插件 | 仅在确定“无路由器且可控制电视端”的需求后做小型 PoC |
| AirPlay | 对应接收设备和受支持的媒体播放路径 | 中；需要单独集成与片源兼容验收 | 有明确 Apple TV/AirPlay 设备需求时再加入 |
| DLNA/自建 TV App/网页配对 | 电视支持对应协议或可运行接收应用 | 中高；设备差异、会话安全、跨网兼容增加 | 先统计目标家庭的实际设备，再决定 |

Cast 依赖本地网络完成发现和控制；同 SSID 不保证能互通（访客网络/AP 隔离等）。通常不要求手机与电视同一 2.4/5 GHz 频段，但路由器必须允许两者及发现流量互通。外网片源仍需电视联网，不能因为“手机能联网”推断电视能取到资源。[Google 发现排查](https://developers.google.com/cast/docs/discovery)。

不能简单沿用“iOS 完全没有标准点对点 Wi-Fi”的旧说法：Apple 已在 iOS 26 提供 Wi-Fi Aware。但 Wi-Fi Aware 是网络连接能力，不能自动变成 Google Cast 或 Miracast，也不能推断普通电视已实现相应服务；本项目还要覆盖 iOS 16。[Apple Wi-Fi API 概览](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview)、[Wi-Fi Aware 与配套设备](https://developer.apple.com/documentation/WiFiAware)、[权限与服务声明](https://developer.apple.com/documentation/wifiaware/adopting-wi-fi-aware)。

## Chromecast 具体实施顺序

1. **先识别目标电视能力。** 记录型号、系统、固件，确认真正支持 Google Cast；不以“智能电视”“Google TV”字样或只有 YouTube 投放成功作为唯一证明。使用既有 Cast 接收端即可；没有则评估外接受支持接收器，不先开发电视 App。本轮没有设备型号信息，因此型号兼容判断仍未完成。
2. **沿用现有数据路径。** `WKWebView → 检测/用户选片 → CastManager → Default Media Receiver → 源站`。手机不转发视频，维护和耗电成本较低。当前代码已用 `kGCKDefaultMediaReceiverApplicationID`；默认接收器无需自建接收网页或注册自己的接收器 App ID。[接收器类型与限制](https://developers.google.com/cast/docs/web_receiver)。
3. **先完成 S1/S2 与可恢复状态。** 输入约束、候选来源、有限连接等待、取消和重试；保持投屏失败手机继续可用、成功确认后才暂停本地。新增输入测试与原有回归一并运行。
4. **减少用户操作。** 现有“投到上次电视”已实现，完善首次本地网络说明和权限恢复；增加固定主电视/忘记设备、常驻 mini remote 的播放暂停入口、无设备超时说明。上次设备发现后仍须由用户点击才发起新投屏。自定义设备选择器需补首次扫描前说明，可评估标准 `GCKUICastButton`，不必重做所有界面。[官方权限与自定义选择器要求](https://developers.google.com/cast/docs/ios_sender/permissions_and_discovery)。
5. **用受控公开 HLS 和 MP4 跑通当前 Release。** 公开测试媒体选择器现在只在 Debug 下可见；验收可用 QA 页面提供同样片源，不必为此打开 Release 调试功能。逐项执行 [ACCEPTANCE.md](../docs/ACCEPTANCE.md)，先验证发现、连接、出画/声、遥控、停止，然后测目标站点、后台/锁屏和 Wi-Fi 恢复。
6. **按失败证据决定升级接收器。** 只有出现字幕/队列/品牌界面/可控鉴权逻辑需求时，才考虑 Custom Web Receiver；届时注册 App ID、HTTPS 托管接收网页、同步 Bonjour App ID，并重新验收。它不能自动绕过源站 Cookie、Referer、反盗链或 DRM。

默认接收器收到的是 URL 和媒体元数据，不是手机 WebKit 的登录会话。网页可播但电视失败时，按编解码、CORS、播放列表/分片/密钥访问、签名有效期分别排查。`.mp4/.m3u8` 只说明容器/协议，不保证电视支持其中的编码。不要为未知失败先传 Cookie、部署开放代理或依赖公共 CORS 代理。只有业务上确需且有权访问的内容，才评估有鉴权、地址限制和清晰生命周期的代理方案；手机代理还会引入 iOS 后台挂起和续流问题。[媒体格式、设备差异与 CORS](https://developers.google.com/cast/docs/media)。

## 可新增功能：按价值排序

| 阶段 | 功能 | 实施与验收边界 |
| --- | --- | --- |
| 先做 | 固定主电视/忘记设备、连接诊断向导、常驻播放暂停、睡眠定时 | 复用现有单会话；定时需明确手机是否要在前台，不能让手机本地计时器承诺锁屏后台可靠停止 |
| 先做 | 无痕浏览与可主动导出的脱敏诊断 | 不保存敏感历史；导出完全由用户触发，诊断字段保持白名单 |
| 后做 | 书签、观看进度/续播、最近播放 | 保存页面及播放位置，避免长期依赖会过期的签名流；恢复后重新解析并再次确认投放设备 |
| 后做 | 字幕/音轨、播放队列、下一集 | 对能够合法获取、接收端支持的媒体轨道和选集元数据实现；不承诺任意网页自动识别全集，分别测字幕 CORS、签名过期与后台续播 |
| 按设备需求 | AirPlay 或 DLNA 适配 | 有实际设备矩阵后再抽通用 Cast 服务接口；先避免把单一 Google SDK 抽象成过度复杂的多协议平台 |
| 暂缓 | TV 原生 App、无路由器 P2P、通用手机代理 | 只有现有 Cast 无法满足已验证的核心场景才投入；会增加部署、权限、安全和兼容维护面 |

建议交付节奏是：**输入加固和测试补洞 → 当前 Release 真机验收 → 操作体验 → 字幕/队列/其它接收协议**。具体工期在电视型号和失败样本明确后估算；本轮没有用不确定的设备能力给出开发天数保证。

# Webcast 深度审查 — 2026-10-24

**结论：当前架构适合自用网页投屏工具，值得继续小步改进。下一轮最有价值的工作是修正“当前视频”和跨页面投屏交接，再验证最新代码在真实电视上的表现。暂时没有证据支持重写、引入代理或扩大功能范围。**

这次审查基于包含未提交修改的当前工作区，而非仅基于 Git HEAD。完整读取了 17 个产品 Swift/JavaScript 文件，共 2,410 行；检查了全部 6 个 XCTest 文件、工程与 CI 配置、资源与隐私清单、两份 README、原始计划、架构决策和既有验收记录。查看了历史组件图，并打开检查本轮重新生成的 6 张窄屏与大字体组件截图。没有修改产品代码、原有测试、版本号或任务账本；新增内容仅为本报告与审查证据。

本轮要求：R1 完整检查当前实现；R2 判断问题、影响与优先级；R3 执行可用验证并区分证据强度；R4 给出聚焦的改进顺序。以下逐项对应。

**总体判断**

| 维度 | 判断 | 原因 |

**已经做对、应保留的部分**

- 完整保留签名 URL，不剥离 token；过滤 blob、带用户名密码的 URL 和非 HTTP(S) 候选。
- 嗅探覆盖主文档及 iframe、原生 media 与 fetch/XHR；HLS master 可继承子列表的分片格式、直播和 DRM 信息。
- 候选上限 100，脚本缓存有界；每个 frame 最多并发检查 4 个响应，每次收集上限 512 KiB、5 秒，不消费网站的原响应。这是检测器的局部限制，不等于整个网页的内存或功耗上限。
- Cast 请求成功与电视确认媒体分开处理；加载失败前保留手机播放，超时可恢复操作。
- 断开后停止轮询；音量拖动做了节流；采用弱消息代理，减少常见 WKWebView 持有环风险。
- Release 隔离调试开关和详细日志；打包检查覆盖嗅探脚本、权限、App 与 SDK 隐私清单。

**优先修正的问题**

优先级含义：P1 为下一轮稳定性工作的优先项；P2 为随后改善；P3 为可后置的维护项。本轮没有发现已证实的 P0 阻断问题，也没有把未执行的电视测试写成通过。

**F1 · P1 · “当前视频”可能被预加载媒体抢走，失效后也不会撤销。已复现。**

位置：[sniff.js](../Webcast/Sniffer/sniff.js) 第 66–80、129–165 行；[VideoCandidate.swift](../Webcast/Models/VideoCandidate.swift) 第 93–103、132–141 行。

`video.src` 赋值和 `setAttribute('src')` 会直接上报 `current: true`。即使视频处于暂停状态、没有加入页面，仍会替换同 frame 的活动 URL。`loadedmetadata`、`durationchange` 也不要求媒体正在播放。另一方面，移除 video 或 iframe 时没有对应的失效消息；`activeByFrame` 只有被另一个 URL 覆盖、超容量淘汰或整体 reset 才清理。

本轮真实 WebKit 复现：

1. 先给 A 发播放事件，再给未加入 DOM、仍为 paused 的预加载 B 设置 src，B 成为置顶“当前视频”。播放事件为夹具合成，不代表下载并解码了真实媒体；它验证的是注入脚本的事件与状态逻辑。
2. 删除已标为当前的 video，页面 video 数变为 0，候选仍为 current。
3. 删除该视频所属 iframe，候选仍为 current。

影响：预加载下一集或广告、播放器替换后，用户可能选到错误或已经失效的视频；问题直接影响核心选择流程。未声称已在某个具体爱壹帆页面发生。

建议：将“发现”“已选源”“播放活动”“推测关联”分开；属性赋值只负责发现，活动状态优先由真实播放器事件和元素存活决定。为 frame/元素增加失效事件，移除、清空来源和 frame 卸载后撤销 current。暂停不必删除候选，避免把正常暂停误判为失效。验收应覆盖预加载、移除元素、移除 iframe、同页广告切换。

**F2 · P1 · 主页面换路由可清空仍存在的 iframe 视频。已复现。**

位置：[VideoSniffer.swift](../Webcast/Sniffer/VideoSniffer.swift) 第 62–64 行；[sniff.js](../Webcast/Sniffer/sniff.js) 第 243–257 行。

主 frame 的 `route` 消息会清空整个 CandidateStore，但随后 `scan()` 只扫描当前 document。已有 iframe 自己的 URL 与去重缓存未变，不会因为父页面路由变化自动重放。结果可能是播放器仍存在，视频列表却为空。

本轮 WebKit 夹具中，主页面 `pushState('/next')` 后，iframe 里的 `persistent.mp4` 仍可通过 DOM 读取，但原生候选列表为空。

另一个已复现边界：hash 路由从 `#/episode/1` 到 `#/episode/2`，同时移除旧播放器，旧集仍保持 current。`routeKey()` 忽略 hash 是为了保留普通锚点，因此不能简单改成“任何 hash 变化都清空”。

建议：以文档、frame 和媒体身份管理候选，在主路由变化时协调所有注入 frame 重新报告，或只失效真正退出的来源；同时依靠媒体生命周期处理 hash router。保留现有普通锚点回归，新增父路由变化而 iframe 不变、frame 内部换页、hash 选集的测试。

**F3 · P1 · 投屏交接保护起点太晚，可能暂停另一页的新视频。代码路径确认；完整电视场景未实测。**

位置：[ContentView.swift](../Webcast/Views/ContentView.swift) 第 61–77、95–109 行；[BrowserModel.swift](../Webcast/Browser/BrowserModel.swift) 第 225–230 行；[CastLoadState.swift](../Webcast/Models/CastLoadState.swift) 第 84–101 行。

可触发顺序：在页面 A 选片 → 尚未连接，保存 `pendingVideo` 并开始连接 → 关闭选择器、在浏览器切到 B → 连接成功后才 `beginLoad(A)`。此时 `.started` 捕获的是 B 的 `documentID` 与 URL；电视确认 A 后，保护检查会认为 B 是应暂停的原页面。

现有保护能处理“请求已发出后再换页”，但覆盖不到“等待连接时换页”。重试旧候选时也需要检查相同边界。另一个模型复现表明，同文档 A→B→A 后，仅比较 document UUID 与 URL 无法识别中间的媒体变化；这只是模型证据，未等同于电视端完整复现。

建议：用户选择时就捕获一个明确的投屏意图，包括候选、浏览器文档/路由版本、必要的媒体身份。连接、重试、确认都沿用这份来源身份。若期间用户换页，可继续履行明确选择的投屏操作，但不可暂停新页面；同时提供明确取消待投屏的入口。验收重点是慢连接、换页、同 URL 换片、关闭选择器、重试旧媒体。

**需要明确产品边界的问题**

**F4 · P2 · 锁屏遥控实现与后台会话策略相冲突。SDK 文档与代码可确认，实际设备行为待验收。**

位置：[CastManager.swift](../Webcast/Cast/CastManager.swift) 第 76–86、374–378 行；[NowPlaying.swift](../Webcast/Cast/NowPlaying.swift) 第 59–81 行。

App 未修改 `suspendSessionsWhenBackgrounded`，其默认值为 true。收到 suspend 后，代码将连接设为 suspended、清空 Now Playing、关闭命令；命令派发又要求 `canControl`。因此不能仅因为接入了 `MPRemoteCommandCenter`，就认为锁屏时可持续控制电视。[Google Cast 后台会话选项](https://developers.google.com/cast/docs/reference/ios/interface_g_c_k_cast_options)。

建议先把验收目标定为“电视继续播放，回到前台能恢复遥控”，与“锁屏中直接遥控”分别验证。前者符合当前轻量架构；后者需要单独研究真实运行条件。不要为满足一个未验证的功能名称，直接增加后台音频或伪保活。

**F5 · P1（验收）· 当前代码的电视端证据落后于代码。**

[README](../README.md) 与[可行性记录](../docs/FEASIBILITY.md) 明确区分了 10 月 7 日的用户播放成功和 10 月 18 日的源码修改，这种诚实应保留。问题是：新代码尚没有相应的逐项接收端验收；62 项测试均在 `WEBCAST_OFFLINE_VALIDATION` 下运行。`GCKRequest.application()` 能验证回调逻辑，但不建立真实 Cast 连接。

下一轮代码修复后，应先产生可区分的版本/build，再用目标 iPhone 与电视验证：目标站至少三集、首次投屏/切集、暂停/Seek/音量/静音/停止、锁屏 30 秒与 5 分钟、短暂 Wi-Fi 中断、加载中换页、连续播放 1–2 小时。记录电视型号、系统版本、媒体类型、结果和恢复时间；不要保存临时签名 URL 的 query 或 Cookie。

目前不足以判断必须增加代理。只有在具体失败样本上证明是认证、CORS 或分片格式问题，才值得评估代理带来的流量、耗电和后台维持成本。

**后续值得做的优化**

**F6 · P2 · 故障信息缺少可诊断的底层原因。**

位置：[CastManager.swift](../Webcast/Cast/CastManager.swift) 第 200–213、388–391、420–428 行。

不同 `GCKError` 最终被压成相同提示，Release 又关闭详细 SDK 日志。这会让“连接失败”“媒体格式不支持”“签名失效”难以区分。建议保留简短主提示，增加用户主动展开的诊断详情：失败阶段、错误码、时间、App build、设备型号、源 host。用小容量本地记录即可；默认不记录完整媒体 URL、token 或页面内容。这样下一次真机失败能产生可行动证据，无需引入后台分析服务。

**F7 · P2/P3 · 官方 SPM 已可用，原依赖选择依据需要更新。**

位置：[project.yml](../project.yml) 第 10–13 行；[PLAN.md](../PLAN.md) 的 SDK 接入说明。

当前锁定 SRGSSR 的 4.8.6；缓存 Package.swift 也表明它从 SRGSSR release 下载二进制并校验 checksum。这个固定版本本身没有被本轮证明存在问题。

但 Google 官方接入文档（页面显示 2026-10-21 更新）已提供 `googlecast/google-cast-ios-sdk`，包含 `GoogleCastDynamic` 与 `GoogleCastStatic`。原计划的“Google 没发 SPM 包”已过时。建议稳定性修复之后，评估保持 4.8.6 的官方 Dynamic 包迁移，减少第三方封装环节；迁移时核查产品名、资源、隐私清单及签名，不必同时改变框架形态。[官方 SPM 接入说明](https://developers.google.com/cast/docs/ios_sender)、[官方仓库](https://github.com/googlecast/google-cast-ios-sdk)。

官方发布说明同时确认 4.8.6 最低支持 iOS 16，因此项目部署目标 16 合理，原 PLAN 中“4.8.6 要求 iOS 15+”应修订。[Google Cast 发布说明](https://developers.google.com/cast/docs/release-notes)。

**F8 · P2（面向多语言用户）· 有翻译文件，不等于动态状态已本地化。**

位置：[ContentView.swift](../Webcast/Views/ContentView.swift) 第 51、55 行；[RemoteView.swift](../Webcast/Views/RemoteView.swift) 第 126 行；[CastErrorAlert.swift](../Webcast/Views/CastErrorAlert.swift) 第 18 行。

字符串目录有 64 个键，每个都包含英文和繁体。但 `connectionLabel`、`playbackLabel`、`errorMessage` 是普通 String，传入 `Text` 时走不自动本地化的重载；一些错误文字也不在目录内。因此英文界面可混入简体状态/错误，不能由“翻译资源已打包”推导出“多语言完整”。[Apple 对 String 与 LocalizedStringKey 的说明](https://developer.apple.com/documentation/SwiftUI/LocalizedStringKey)。

建议仅本地化 App 自己的状态与错误，网站标题和用户设备名继续原样展示。中文自用场景可后置，公开多语言版本前应修正，并实际渲染已连接、加载失败与重试状态。

**UI 与日常体验的判断**

保留原生 SwiftUI、teal 强调色、现有三个标签页。本轮 6 张组件图覆盖 320×568pt 视口的起始页、未连接遥控页、视频列表和设置页：普通字号层次清楚，大字体内容依靠滚动访问；没有提供必须重设计的证据。截图为离线 Debug，投屏按钮禁用及 Debug 区域属于测试状态；完整连接状态、深色模式、横屏、滚动操作和 VoiceOver 仍未验收。

下一步界面优化应服务选择与恢复：同一页面 title、CDN host 相同且时长未知时，多个候选几乎无法区分。可以给重复项增加可展开的简短来源路径、格式或“最近播放/已失效”等信息；避免重新把所有技术参数常驻铺满。先修正 F1 的状态语义，再增加“推荐”提示。

“找不到电视”已有帮助，可补系统设置入口和明确的扫描反馈；不要仅凭设备列表为空就声称权限被拒绝。连接中与等待恢复阶段应有一致的取消/退出路径。书签、历史、字幕、队列、广告过滤都属于功能扩展，暂时排在稳定性之后。

**测试与工程维护建议**

- 保留现有真实 WebKit 测试。新增测试集中在 F1/F2 的 frame 生命周期，以及 F3 的完整用户操作序列。
- 把投屏意图与会话协调从 `ContentView` 的若干 `@State`/`onChange` 中提取成一个小的可测试对象；仅对需要模拟的 SDK 边界增加接口。没有必要为 2,410 行产品代码铺设大型架构框架。

- App 最低 iOS 16，但测试 target 最低 17，本机仅有 18.6/26.5。需要给 iOS 16 留出真机/模拟器 smoke test，或在未来基于用户范围调整支持承诺。
- CI 使用 macos-15 并动态选择最新 iOS，未显式固定 Xcode；本机当前为 Xcode 27.1，文档记录 27.0。建议输出并明确固定一条基准工具链，另设升级验证；本轮没有执行远端 CI，也没有据此判断远端已失败。
- 下一次安装前更新 build 编号，保留“源码—构建—安装—电视验收”的对应关系。历史 0.1.1 (2) 成功不能自动覆盖同版本号的新代码。
- 原 PLAN 的早期状态与 SDK 说明已经落后于后续验收记录。将其明确标记为历史决策，当前状态统一指向 README 与最新验收记录，减少以后重复争论已解决的问题。
